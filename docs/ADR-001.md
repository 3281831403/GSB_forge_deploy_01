# ADR-001 v2 — Forge Stable Identity, Symbol Allocation, File Ownership, and Extension ABI

**Status:** Proposed — intended to be locked before F0
**Product:** Gombit Forge
**Repository:** `gombit-forge`
**Decision scope:** Project identity, symbol lifetime, generated/user file ownership, backend extension ABI, mutation compatibility, orphan handling, identity continuity
**Supersedes:** ADR-001 v1
**Related design:** Gombit Forge MVP Design Document v2
**Related future ADRs:**

* ADR-002 — Managed Local Toolchain and Runtime Preview
* ADR-003 — Gombit Migration Intent & Safety Manifest
* Future ADR — Frontend Extension ABI

---

# 1. Context

Gombit Forge is a local-first visual application builder that compiles a declarative `ProjectSpec` into an ordinary Gombit application.

Forge must satisfy two requirements that naturally conflict:

1. Forge must repeatedly regenerate application structure from `ProjectSpec`.
2. Users must be able to add custom behavior without permanently ejecting the project from Forge.

A pure generator creates an unacceptable cliff:

```text
No code
   ↓
Need one custom behavior
   ↓
Export / eject
   ↓
Forge can no longer manage the project
```

Allowing users to freely modify generated files creates the opposite failure mode:

```text
ProjectSpec
   ↓
Generated source
   ↓
Arbitrary user edits
   ↓
Forge regeneration
   ↓
Need bidirectional reconciliation
```

Forge explicitly rejects arbitrary bidirectional source reconciliation.

The adopted model is:

```text
                    ProjectSpec
                         │
                         ▼
                   Forge Compiler
                         │
          ┌──────────────┴──────────────┐
          │                             │
          ▼                             ▼
 compiler-owned structure        versioned extension ABI
                                        │
                                        ▼
                                  user-owned behavior
```

Forge therefore owns **structure**.

Developers may own **behavior** behind explicit, narrow, versioned seams.

The difficult compatibility problem is intentionally reduced to:

> Can a candidate `ProjectSpec` preserve, extend, or explicitly break the generated API that user-owned extension code depends upon?

This ADR defines that contract.

---

# 2. Decision summary

Forge adopts the following rules.

## D1 — Semantic identity is permanent

Every addressable semantic object receives an immutable opaque stable ID when created.

Examples:

```text
prj_...
res_...
fld_...
rel_...
pag_...
act_...
hok_...
```

The ID represents identity.

Names do not.

---

## D2 — Labels, storage names, and code symbols are separate

Every generated entity has distinct naming domains.

Example:

```text
Stable ID:     fld_01K...
Label:         Contact email
Storage name:  contact_email
Code symbol:   Email
```

A change to one does not automatically imply a change to the others.

---

## D3 — Code symbols are minted once and frozen

Every source-level symbol is allocated when its semantic entity is created.

The allocated symbol remains attached to that stable ID until an explicit breaking source refactor changes it.

Normal relabeling or storage renaming does not change the source symbol.

---

## D4 — Allocated symbols remain reserved for the project lifetime

A source symbol is never silently recycled for a different semantic entity.

Deleting an entity tombstones its symbol.

Example:

```text
fld_A → Email
```

is deleted.

A later unrelated field may not automatically acquire `Email`.

This prevents historical or orphaned code from appearing to refer to a new semantic entity.

---

## D5 — Symbol allocation is collision-aware

Source symbols must be unique in their generated namespace.

Allocation considers:

* live symbols;
* tombstoned symbols;
* framework-reserved names;
* generated helper names;
* language restrictions;
* namespace-specific reserved identifiers.

Collisions are resolved at mint time.

---

## D6 — Source-symbol changes are explicit breaking refactors

Forge never changes:

```text
Email → ContactEmail
```

merely because a label or database column changed.

A code-symbol rename is a distinct source refactor and must pass compatibility validation.

---

## D7 — Compiler-owned and user-owned files never share ownership

Forge-owned code lives under explicit generated directories.

User-owned code lives under explicit extension directories.

No marker regions.

No partial ownership.

---

## D8 — Forge never rewrites existing user implementation code

Forge may create an extension stub once.

After creation, the file belongs to the user.

Forge may:

* compile it;
* inspect its existence;
* surface diagnostics referring to it;
* archive it when explicitly requested.

Forge must not rewrite its implementation.

---

## D9 — Extensions bind to a deliberately narrow generated ABI

Extensions do not depend directly on arbitrary generated GORM models, handler internals, or compiler implementation structures.

The extension ABI is explicitly designed and independently versioned.

---

## D10 — Read and mutation surfaces are intentionally different

After-hooks receive immutable views.

Before-hooks receive controlled mutable draft/change objects.

Mutation does not require exposing raw persistence structures.

---

## D11 — ABI-neutral edits do not require user code to compile

Forge distinguishes:

```text
Spec validity
ABI compatibility
Current project build health
```

A user may temporarily have broken extension code.

That must not prevent unrelated ABI-neutral visual editing.

---

## D12 — ABI-breaking edits require compatibility validation

A transition that changes the supported extension ABI cannot become the current committed spec until candidate compatibility has been validated.

---

## D13 — Deleted-resource extension code is archived outside the Go build graph

User code for a deleted resource must not remain beneath an active module package path where `go build ./...` can discover dangling imports.

Forge preserves it outside the active source tree.

---

## D14 — Migration inference requires verified identity continuity

Forge infers operations such as rename only when stable IDs form a trustworthy lineage from the previous accepted revision.

If identity continuity is broken through hand-editing or Git merge, Forge fails closed rather than guessing.

---

## D15 — Exported metadata is inert provenance

An exported source repository may retain Forge metadata for traceability.

That metadata is not a promise that Forge can reconstruct arbitrary post-export source modifications.

No round-trip reconciliation is implied.

---

## D16 — Backend Go extensions are in scope; frontend ABI is not

ADR-001 v2 defines the Go/backend extension model.

Frontend extension ownership directories may be reserved, but no supported React/TypeScript extension ABI is defined here.

Frontend extensions require a separate ADR.

---

# 3. Semantic identity model

A resource may be represented as:

```json
{
  "id": "res_01K2M6RXQ8CJ...",
  "label": "Customer",
  "code_name": "Customer",
  "storage_name": "customers"
}
```

A field:

```json
{
  "id": "fld_01K2M7...",
  "resource_id": "res_01K2M6...",
  "label": "Email",
  "code_name": "Email",
  "storage_name": "email",
  "type": "string"
}
```

Semantics:

| Property       | Purpose                  | Mutation rule                            |
| -------------- | ------------------------ | ---------------------------------------- |
| `id`           | Semantic identity        | Immutable                                |
| `label`        | Human presentation       | Freely mutable                           |
| `storage_name` | Database/storage mapping | Mutable through migration intent         |
| `code_name`    | Generated source ABI     | Frozen unless explicit breaking refactor |

---

# 4. Identity is not naming

The system must never infer identity from names alone.

These two states:

```text
Before:
ID: fld_A
Label: Email
Storage: email
Code: Email
```

```text
After:
ID: fld_A
Label: Contact email
Storage: contact_email
Code: Email
```

represent one semantic field.

By contrast:

```text
Before:
ID: fld_A
Storage: email
```

```text
After:
ID: fld_B
Storage: contact_email
```

does **not** prove a rename.

It may mean:

* old field deleted, new field created;
* manual identity corruption;
* merge conflict resolution;
* intentional replacement.

Forge must not guess.

---

# 5. Symbol minting

Symbol allocation is a first-class compiler operation.

It is not an incidental transformation of a label.

When an entity is created:

```text
User label
    ↓
normalize candidate
    ↓
validate language rules
    ↓
check symbol ledger
    ↓
check reserved names
    ↓
disambiguate if necessary
    ↓
freeze symbol
```

---

# 6. Symbol normalization

A label is converted into a candidate source identifier according to deterministic rules.

Examples:

```text
"email"              → Email
"contact email"      → ContactEmail
"created-at"         → CreatedAt
"2 factor enabled"   → TwoFactorEnabled or Field2FactorEnabled
```

The exact lexical normalization rules belong to the compiler implementation specification, but they must be:

* deterministic;
* stable across supported compiler versions unless deliberately versioned;
* compatible with Go identifiers;
* human-readable.

---

# 7. Symbol namespace

Allocation occurs inside a specific generated namespace.

Examples:

```text
Resource type namespace

Customer field/accessor namespace

Project field/accessor namespace

Generated lifecycle-hook namespace
```

Two fields in different resources may both legitimately have:

```text
Email
```

Two fields in the same generated resource ABI may not.

---

# 8. Collision handling

Suppose a user creates:

```text
Field label: Email
```

Forge allocates:

```text
Email
```

The field is later relabeled:

```text
Primary contact
```

but retains:

```text
Email
```

The user then creates a new field labeled:

```text
Email
```

Forge must not allocate `Email` again.

A deterministic fallback is selected:

```text
Email2
```

Then:

```text
Email3
Email4
...
```

as necessary.

The disambiguated symbol is frozen immediately.

---

# 9. Why collisions are resolved at mint time

A frozen ABI means collision repair after creation would itself be a breaking change.

Therefore the allocator must ensure uniqueness before the entity becomes part of an accepted `ProjectSpec`.

Forge must never create a state requiring an immediate breaking refactor merely to compile.

---

# 10. Tombstoned symbols

When a semantic entity is deleted, its code symbol remains reserved.

Example:

```text
fld_A
code_name = Email
```

is deleted.

The project's symbol ledger records:

```text
Email → tombstoned
```

A future unrelated field cannot automatically reuse it.

Reasons include:

* old extension source may still exist;
* archived source may refer to the old symbol;
* Git history contains that API;
* exported source may have exposed it;
* reuse would make unrelated semantic entities look identical at source level.

---

# 11. Symbol ledger

Forge maintains logical source-symbol history.

Conceptually:

```json
{
  "resource": {
    "Customer": {
      "status": "live",
      "entity_id": "res_A"
    }
  },

  "fields:res_A": {
    "Email": {
      "status": "tombstoned",
      "entity_id": "fld_A"
    },

    "Email2": {
      "status": "live",
      "entity_id": "fld_B"
    }
  }
}
```

The exact on-disk representation is not locked by this ADR.

The semantic requirement is.

---

# 12. Reserved symbols

The allocator must reject or disambiguate symbols that collide with generated/framework requirements.

Possible examples:

```text
ID
Validate
Create
Update
Delete
Hooks
Register
Metadata
```

Whether each specific name is reserved depends on the generated ABI design.

The compiler must own an explicit reservation table rather than discovering collisions only when `go build` fails.

Go language restrictions are also enforced.

---

# 13. Explicit code-symbol refactoring

A user may deliberately request:

```text
Email → ContactEmail
```

as a generated API change.

That operation is distinct from:

```text
Label:
Email → Contact email
```

or:

```text
Storage:
email → contact_email
```

A source-symbol refactor:

1. updates the candidate ABI;
2. updates the symbol ledger;
3. creates a candidate generated tree;
4. preserves user extension code unchanged;
5. performs compatibility validation;
6. rejects the candidate if incompatible user code remains.

---

# 14. Optional code-name normalization

Frozen symbols can result in creation-time terminology remaining in exported source.

Example:

```text
UI label: Client
Code symbol: Customer
```

This is accepted during managed operation.

Forge may later expose:

```text
Normalize generated identifiers
```

This operation performs explicit source refactors toward current labels.

It must:

* never run automatically;
* never run merely because the user exports;
* classify itself as ABI-breaking;
* require candidate validation.

Proposed project structure:

```text
my-app/

│   └── server/
│
├── internal/
│   ├── forge_generated/
│   │   ├── customer/
│   │   │   ├── model.go
│   │   │   ├── contract.go
│   │   │   ├── handlers.go
│   │   │   ├── routes.go
│   │   │   └── extension_api.go
│   │   │
│   │   └── project/
│   │
│   └── extensions/
│       ├── customer/
│       │   └── hooks.go
│       └── project/
│           └── hooks.go
│
├── frontend/
│   └── src/
│       └── forge_generated/
│

│   └── migrations/
│
├── forge.json

```

# 16. Compiler-owned files

Everything beneath:

```text
internal/forge_generated/
```

is wholly owned by Forge.

Files contain:

```go
// Code generated by Gombit Forge. DO NOT EDIT.
```

Forge may:

* delete them;
* recreate them;
* reorder them;
* split packages;
* change internal implementations;
* replace them entirely.

Users must assume direct edits will be lost.

---

# 17. User-owned files

Everything beneath:

```text
internal/extensions/
```

is user-owned.

Forge may:

* include it in builds;
* observe whether files exist;
* surface diagnostics;
* identify extension/resource association;
* archive it after explicit user approval.

Forge must not rewrite the implementation.

---

# 18. No mixed ownership

Rejected:

```go
// FORGE:BEGIN
generated code
// FORGE:END

user code

// FORGE:BEGIN
generated code
// FORGE:END
```

Forge does not use region-based generation.

Reasons:

* markers can be deleted;
* formatters alter surrounding structure;
* Git merges become fragile;
* ownership becomes ambiguous;
* AST and text rewriting complexity grows;
* users cannot know which refactors are safe.

Ownership is at file or directory level.

---

# 19. No AST rewriting of user implementation code

Forge may use structured code generation internally.

It may not use `go/ast` rewriting to silently repair extension implementations after an ABI change.

If a source-level breaking change requires changing user code, Forge reports the incompatibility.

The developer owns the fix.

---

# 20. Backend extension surface

F0 supports a deliberately narrow backend lifecycle extension model.

Initial candidates:

```text
BeforeCreate
AfterCreate

BeforeUpdate
AfterUpdate

BeforeDelete
AfterDelete
```

The number of supported lifecycle events should remain small.

This ADR does not establish a general plugin system.

---

# 21. Immutable after-hook views

After-hooks receive immutable generated views.

Conceptually:

```go
type CustomerView interface {
    ID() CustomerID
    Email() string
    Name() string
}
```

Example:

```go
func (Hooks) AfterCreate(
    ctx context.Context,
    customer generated.CustomerView,
) error {
    return sendWelcomeEmail(customer.Email())
}
```

The underlying GORM model is not exposed as the ABI by default.

---

# 22. Why immutable views exist

Exposing:

```go
*Customer
```

where `Customer` is also the generated persistence model would make all of these public compatibility constraints:

* field layout;
* ORM tags;
* embedded model choices;
* persistence helper methods;
* GORM-specific internals;
* future storage implementation decisions.

The extension view deliberately narrows the promise.

---

# 23. Stable accessors

Generated accessor names derive from frozen source symbols.

Example:

```text
Stable ID: fld_A
Code symbol: Email
```

generates:

```go
Email() string
```

Changing:

```text
Label: Email → Contact email
Storage: email → contact_email
```

does not change:

```go
Email() string
```

Therefore existing hooks remain source-compatible.

---

# 24. Before-hook mutation model

Before-hooks require a controlled mutable surface.

Read-only views are insufficient.

Useful before-hook behavior includes:

```text
normalize values
compute values
set defaults
reject input
add field-scoped validation errors
modify selected updates
```

Forge therefore exposes generated draft/change objects rather than raw persistence models.

---

# 25. CreateDraft contract

Conceptually:

```go
func (Hooks) BeforeCreate(
    ctx context.Context,
    draft *generated.CustomerCreateDraft,
) error
```

The draft exposes generated accessor and mutator methods:

```go
draft.Email()
draft.SetEmail("user@example.com")

draft.Name()
draft.SetName("Alice")
```

The concrete internal storage fields need not be exported.

---

# 26. CreateDraft semantics

A create draft represents the candidate value before persistence.

For each writable field, Forge may generate:

```go
Email() string
SetEmail(string)

Name() string
SetName(string)
```

Nullable fields require explicit nullable semantics rather than ambiguous zero values.

Exact nullable API shape is provisional for F0 experimentation.

The following invariant is locked:

> Extension mutation occurs through the stable generated contract, not by directly mutating generated ORM structs.

---

# 27. Validation rejection

Before-hooks may reject the operation using ordinary Go errors.

Forge should also provide structured validation errors so UI/API responses can associate an error with a semantic field.

Conceptually:

```go
return forge.InvalidField(
    generated.FieldEmail,
    "email domain is not allowed",
)
```

A generated field reference is tied to stable field identity.

Example conceptually:

```go
var FieldEmail forge.FieldRef
```

The actual API is subject to F0 refinement.

The requirement is that field-specific rejection remains stable across label/storage renames.

---

# 28. BeforeUpdate is not BeforeCreate

Updates have presence semantics.

Forge must distinguish:

```text
field not included in update
```

from:

```text
field explicitly changed to its zero value
```

Therefore update hooks receive a change set.

Conceptually:

```go
func (Hooks) BeforeUpdate(
    ctx context.Context,
    current generated.CustomerView,
    changes *generated.CustomerUpdateChanges,
) error
```

---

# 29. UpdateChanges semantics

Possible generated API:

```go
email, changed := changes.Email()

if changed {
    changes.SetEmail(strings.ToLower(email))
}
```

Nullable fields may additionally support:

```go
changes.ClearNickname()
```

or equivalent explicit semantics.

F0 must prove that:

* absence is distinguishable from zero value;
* changed values can be read;
* changed values can be replaced;
* nullability is explicit.

---

# 30. BeforeDelete

Deletion mutation is naturally narrower.

A possible contract is:

```go
func (Hooks) BeforeDelete(
    ctx context.Context,
    current generated.CustomerView,
) error
```

The hook may reject deletion.

There is generally no mutable deletion draft.

---

# 31. AfterUpdate and AfterDelete

After-update receives an immutable final view.

Potentially:

```go
func (Hooks) AfterUpdate(
    ctx context.Context,
    current generated.CustomerView,
) error
```

If both prior and final state are later demonstrated necessary, that can be an additive ABI evolution or separate design decision.

After-delete may receive an immutable snapshot of the deleted record.

F0 should avoid overdesigning historical-state APIs.

---

# 32. Extension ABI version

The backend extension contract has an explicit independent version.

Example:

```json
{
  "forge": {
    "spec_version": 1,
    "compiler_version": "0.1.0",
    "extension_abi_version": 1,
    "gombit_protocol_version": 1
  }
}
```

These version domains represent different contracts and must not be conflated.

---

# 33. Generated implementation freedom

Provided the supported ABI remains compatible, Forge may freely change generated internals such as:

```text
GORM model layout
handler structure
package internals
route plumbing
validation implementation
admin registration
compiler helper structure
```

The extension ABI exists precisely to preserve this freedom.

---

# 34. Hook registration

Extension discovery must be deterministic and statically typed.

Forge should not depend on runtime filesystem discovery or reflection.

Generated code may explicitly register hooks:

```go
extensions.RegisterCustomerHooks(
    customerhooks.New(),
)
```

The exact API is provisional.

Requirements:

* compile-time type safety;
* deterministic registration;
* generated wiring;
* no request-time reflective discovery.

---

# 35. Creating a hook

When the user enables:

```text
Customer
  → Lifecycle
      → After Create
```

Forge updates compiler-owned registration/contract code.

If no user implementation exists, Forge may offer to create:

```text
internal/extensions/customer/hooks.go
```

exactly once.

Example:

```go
package customer

import (
    "context"

    generated "example/internal/forge_generated/customer"
)

type Hooks struct{}

func (Hooks) AfterCreate(
    ctx context.Context,
    customer generated.CustomerView,
) error {
    return nil
}
```

Once created, the file becomes user-owned permanently.

---

# 36. Spec validity, ABI compatibility, and build health

Forge tracks three separate states.

## Spec validity

Does the semantic application model make sense?

Examples of invalid states:

```text
relationship references deleted resource
duplicate stable ID
invalid storage identifier
unsupported field type
```

---

## ABI compatibility

Does the candidate generated extension contract remain compatible with the currently accepted user-facing ABI?

---

## Project build health

Does all current generated and user code compile?

These states are not equivalent.

Example:

```text
Spec:             valid
ABI:              unchanged
Project build:    broken due to half-written hooks.go
```

This must remain an editable project.

---

# 37. Candidate mutation pipeline

All committed structural mutations begin with a candidate state.

```text
Current ProjectSpec
        │
        ▼
Candidate ProjectSpec
        │
        ▼
semantic validation
        │
        ▼
ABI diff / contract analysis
        │
      classify
        │
   ┌────┼─────────┐
   │    │         │
neutral additive breaking
```

Validation requirements depend on classification.

---

# 38. Class A — ABI-neutral transitions

Examples:

```text
human label changes
help text
page ordering
navigation changes
storage rename with frozen source symbol
dashboard arrangement
unrelated presentation metadata
```

Forge must prove that the generated extension ABI is unchanged.

A practical implementation may compare normalized/fingerprinted generated contracts.

If the ABI is unchanged:

> The candidate may commit without requiring user extension code to compile.

This prevents unfinished custom code from freezing the visual editor.

---

# 39. ABI fingerprint

Forge should generate a normalized representation of the supported backend extension surface.

Conceptually:

```json
{
  "resource": "res_A",
  "hooks": {
    "AfterCreate": {
      "input": "CustomerView"
    }
  },
  "view": {
    "Email": "string",
    "Name": "string"
  }
}
```

A stable digest may be calculated:

```text
extension_abi_sha256
```

For an ABI-neutral transition:

```text
old fingerprint == candidate fingerprint
```

means user-code compilation is unnecessary for compatibility purposes.

This does not claim that the user's project currently builds.

---

# 40. Class B — backward-compatible additive transitions

Examples may include:

```text
new independent resource
new contract unused by existing implementation
new optional extension point
```

However, “additive” in source text is not automatically backward-compatible.

For example, adding a required method to a Go interface implemented by user code is breaking.

Therefore Forge classifies compatibility semantically rather than assuming:

```text
new thing = safe
```

If compatibility can be proven without compiling user code, the candidate may commit.

Otherwise candidate typechecking is required.

---

# 41. Class C — ABI-breaking transitions

Examples:

```text
field accessor removal
extension-visible field type change
resource deletion
relationship contract change
explicit source-symbol rename
removal of hook contract
incompatible mutation API change
```

Class C requires candidate compatibility validation.

The candidate cannot become current while incompatible user extension code remains.

---

# 42. Candidate compilation for breaking transitions

For a breaking transition:

```text
candidate spec
      ↓
temporary workspace
      ↓
new generated contracts
      +
copied user extensions
      ↓
typecheck/build
```

If extension code is incompatible, Forge rejects the spec transition.

The current accepted revision remains unchanged.

---

# 43. Broken user code does not globally freeze Forge

If user code is already broken before a Class C mutation, Forge may be unable to establish compatibility.

That Class C mutation must remain blocked until the relevant build/typecheck can succeed.

However, unrelated Class A edits remain allowed.

The UI should distinguish:

> Current Runtime Build is broken.

from:

> This candidate spec change itself is invalid.

---

# 44. Atomic editing transactions

Users may need to perform logically related changes together.

Example:

```text
delete relationship Project.Customer
delete Customer resource
```

Persisting the first click and validating every intermediate state independently can produce awkward or impossible workflows.

Forge therefore supports:

```text
valid committed revision
        ↓
editing transaction
        ↓
candidate graph
        ↓
validate whole candidate
        ↓
next valid revision
```

Only accepted candidate states enter revision history.

---

# 45. Resource deletion dependency analysis

Before deleting a resource, Forge checks:

```text
relationships
pages
filters
forms
permissions
admin configuration
hooks
extension registrations
migration consequences
```

If a hard dependency remains, deletion is rejected before generation.

---

# 46. Extension archival on resource deletion

User extension code for a deleted resource must not remain beneath:

```text
internal/extensions/
```

if its generated dependency is being removed.

Instead, after explicit user approval, Forge archives it outside the active Go source tree.

Example:

```text
.forge/
└── orphaned/
    └── 2026-08-24T210000Z/
        └── customer/
            └── hooks.go
```

The precise archival key may use revision IDs rather than timestamps.

---

# 47. Archive semantics

Archived user code:

* is not rewritten;
* is not included in active hook registration;
* is outside normal application package traversal;
* remains available for manual recovery;
* is associated with its original resource stable ID in Forge metadata.

Forge must not silently delete custom source.

---

# 48. Why in-place orphaning is rejected

Leaving:

```text
internal/extensions/customer/hooks.go
```

after deleting:

```text
internal/forge_generated/customer/
```

creates dangling imports.

A subsequent:

```bash
go build ./...
```

may fail even though Forge claims the deleted extension is inactive.

Therefore inactive preserved extensions must leave the active build graph.

---

# 49. Mutation scenario A — relabel field used by hook

Initial:

```text
Stable ID:    fld_A
Label:        Email
Storage:      email
Code symbol:  Email
```

Hook:

```go
func (Hooks) AfterCreate(
    ctx context.Context,
    customer generated.CustomerView,
) error {
    return sendWelcome(customer.Email())
}
```

User changes:

```text
Label:
Email → Contact email

Storage:
email → contact_email
```

Candidate:

```text
Stable ID:    fld_A
Label:        Contact email
Storage:      contact_email
Code symbol:  Email
```

Effects:

```text
UI label           changed
storage mapping    changed
migration intent   rename
extension ABI      unchanged
hook source        unchanged
```

Result:

**Class A / ABI-neutral.**

No user-code compilation is required merely to accept this rename.

---

# 50. Mutation scenario B — duplicate visible name

Initial:

```text
fld_A
Label: Primary contact
Code:  Email
```

A new field is created with:

```text
Label: Email
```

Allocator sees:

```text
Email → already reserved by fld_A
```

and mints:

```text
fld_B
Label: Email
Code:  Email2
```

Result:

**Accepted.**

No collision enters the project.

---

# 51. Mutation scenario C — add a hook to populated resource

Existing:

```text
Customer
50,000 persisted rows
no custom lifecycle hooks
```

User enables:

```text
AfterCreate
```

Forge:

1. adds compiler-owned contract/registration;
2. offers one-time extension stub creation;
3. does not modify schema merely for hook registration;
4. validates the candidate ABI/build as required;
5. preserves existing data.

Result:

**Accepted if the candidate contract is valid.**

---

# 52. Mutation scenario D — mutable BeforeCreate

Given:

```text
Customer.Email
```

a hook:

```go
func (Hooks) BeforeCreate(
    ctx context.Context,
    draft *generated.CustomerCreateDraft,
) error {
    draft.SetEmail(strings.ToLower(draft.Email()))

    if strings.HasSuffix(draft.Email(), "@invalid.test") {
        return forge.InvalidField(
            generated.FieldEmail,
            "unsupported email domain",
        )
    }

    return nil
}
```

must:

* mutate the final persisted value;
* preserve source compatibility across label/storage rename;
* surface structured rejection;
* avoid direct GORM access.

This is a mandatory F0 proof.

---

# 53. Mutation scenario E — mutable BeforeUpdate

Given an update where:

```text
Email is absent
```

the hook must distinguish it from:

```text
Email explicitly changed to ""
```

Conceptually:

```go
email, changed := changes.Email()

if changed {
    changes.SetEmail(strings.TrimSpace(email))
}
```

F0 must prove update presence semantics.

---

# 54. Mutation scenario F — delete referenced resource

Initial:

```text
Customer
    ▲
    │ belongs_to
Project
```

and:

```text
internal/extensions/customer/hooks.go
```

User attempts:

```text
Delete Customer
```

Forge identifies:

* `Project.Customer` relationship;
* active lifecycle extension;
* persisted table deletion consequences.

The candidate is rejected until dependencies are resolved.

If deletion later proceeds, user extension source is archived outside the build graph.

No invalid committed revision is produced.

---

# 55. Mutation scenario G — relabel versus code rename

Initial:

```text
Label: Customer
Code:  Customer
```

Normal visual rename:

```text
Label: Client
Code:  Customer
```

Result:

**ABI-neutral.**

Existing code continues using:

```go
CustomerView
```

If the user separately chooses:

```text
Refactor source symbol:
Customer → Client
```

Forge classifies it as breaking.

Candidate contract changes to:

```go
ClientView
```

Existing user code may fail typechecking.

The transition remains uncommitted until compatible.

---

# 56. Mutation scenario H — field type change

Initial extension ABI:

```go
Quantity() int
```

User changes the semantic field type:

```text
integer → string
```

Candidate ABI:

```go
Quantity() string
```

Stable identity alone cannot preserve source compatibility.

This is Class C.

Forge must validate:

* extension compatibility;
* migration safety;
* page/form compatibility;
* generated API semantics.

---

# 57. Identity continuity

Migration and semantic diffing rely on stable IDs being trustworthy.

Forge-managed mutations naturally preserve lineage.

Local-first projects, however, can be:

* hand-edited;
* changed by scripts;
* merged through Git;
* restored from unusual history.

Therefore the current disk spec cannot automatically be assumed to descend safely from the last accepted Forge revision.

---

# 58. Identity discontinuity detection

Suppose the last accepted revision contains:

```json
{
  "id": "fld_A",
  "storage_name": "email"
}
```

The on-disk spec suddenly contains:

```json
{
  "id": "fld_B",
  "storage_name": "contact_email"
}
```

Forge must not infer:

```text
rename email → contact_email
```

because identity changed.

The safe classification is:

```text
identity continuity unknown
```

---

# 59. Identity discontinuity behavior

When lineage cannot be established, Forge refuses automatic destructive or rename inference.

The user may be asked to resolve the semantic relationship explicitly.

Possible choices:

```text
Treat as rename of fld_A
Treat as delete fld_A + add fld_B
Restore previous stable identity
Cancel
```

Exact UX is outside this ADR.

The invariant is:

> Forge fails closed when identity continuity is uncertain.

---

# 60. Revision lineage

Each accepted revision should contain enough metadata to establish ancestry.

Conceptually:

```json
{
  "revision_id": "rev_B",
  "parent_revision_id": "rev_A",
  "project_spec_hash": "..."
}
```

Git remains complementary.

Forge revision lineage is the basis for automatic semantic migration inference.

---

# 61. External merge handling

A Git merge may produce a syntactically valid spec while semantically corrupting IDs.

Therefore reopening a project after external file changes requires semantic lineage validation.

Forge should distinguish:

```text
valid external edit
```

from:

```text
identity-discontinuous edit
```

A valid external label change preserving IDs can remain safe.

An arbitrary ID rewrite cannot.

---

# 62. Interaction with migration intent

Stable identity supports operations such as:

```text
same fld_A
email → contact_email
```

therefore:

```text
rename_column
```

But this ADR does not define executable migration safety policy.

That belongs to ADR-003.

This ADR establishes the prerequisite:

> Automatic migration intent is valid only when semantic identity lineage is valid.

---

# 63. Frontend scope

ADR-001 v2 deliberately does **not** define a supported frontend extension ABI.

The following questions remain unresolved:

```text
What is a stable component contract?
Do extensions bind to generated props?
Generated resource hooks?
Route contexts?
Form slots?
Field registries?
```

TypeScript's compatibility model also differs from Go's.

Therefore F0 does not attempt to prove backend/frontend symmetry.

---

# 64. Frontend generated ownership

Forge may still reserve:

```text
frontend/src/forge_generated/
```

as compiler-owned.

A future:

```text
frontend/src/extensions/
```

may become user-owned once an explicit frontend extension ABI exists.

Until then, Forge must not advertise arbitrary React extensions as a supported managed-mode feature.

---

# 65. Design Preview

Design Preview operates from `ProjectSpec`.

It does not execute backend extension code.

Forge must clearly label this fidelity boundary.

Examples:

> Custom lifecycle hooks are not executed in Design Preview.

> Runtime permission behavior may differ from this structural preview.

Design Preview must not pretend to validate runtime extension behavior.

---

# 66. Runtime Preview and toolchain requirement

Class C compatibility validation and Runtime Preview require real typechecking/building.

Therefore they require a functioning managed or system toolchain.

The broader product design locks a managed local-toolchain fallback.

ADR-002 defines its provisioning and execution mechanics.

---

# 67. Toolchain-unavailable behavior

If a candidate mutation requires compilation and no usable toolchain exists:

Forge must not silently accept the mutation.

It should surface something equivalent to:

> This change modifies the generated extension API and must be type-checked before it can be committed.

Then:

```text
Install managed toolchain
Configure existing toolchain
Cancel
```

ABI-neutral edits remain available.

---

# 68. Gombit integration boundary

Forge communicates with Gombit through a coarse versioned machine interface rather than depending primarily on unstable internal generator packages.

Conceptually:

```text
Forge
   │
   │ complete structured project request
   ▼
Gombit machine generation contract
   │
   ▼
Generated Gombit project
```

Requirements:

* versioned protocol;
* structured input/output;
* machine-readable diagnostics;
* one coarse project-level invocation;
* pinned Gombit version;
* deterministic behavior.

---

# 69. No chatty generator protocol

Rejected:

```text
spawn gombit for Customer
spawn gombit for Project
spawn gombit for Ticket
spawn gombit for each page
...
```

Preferred:

```text
one project model
      ↓
one coarse generation operation
```

The split between Forge and Gombit should not create excessive local subprocess overhead.

---

# 70. Project serialization

ProjectSpec serialization must preserve:

```text
stable IDs
frozen source symbols
symbol tombstones or reconstructible symbol history
revision identity
deterministic ordering
```

It must also be Git-friendly.

Semantically identical specs should not receive unrelated formatting churn.

---

# 71. Build health diagnostics

Forge should separately expose:

```text
Spec
Extension compatibility
Runtime build
```

Example UI state:

```text
Spec                   ✓ Valid
Extension ABI          ✓ Compatible
Runtime Build          ✗ hooks.go:42 syntax error
```

This makes it clear why visual editing may continue while Runtime Preview cannot.

---

# 72. Export semantics

Export produces ordinary source code.

After export:

> Every file is user-owned.

Forge-generated banners may remain informational.

The exported project has no Forge runtime dependency.

---

# 73. Export metadata

Export may include inert provenance such as:

```json
{
  "generated_by": "gombit-forge",
  "compiler_version": "0.1.0",
  "spec_version": 1,
  "source_project_revision": "rev_..."
}
```

Stable IDs may be retained for auditability.

However:

> Export metadata is not a bidirectional synchronization anchor.

Forge must not promise that arbitrary post-export source changes can later be reconciled with the original visual model.

---

# 74. Managed project versus exported repository

The conceptual boundary is:

```text
Forge-managed project
       │
       ├──────── continues in Forge
       │
       └── Export
             │
             ▼
      ordinary source repository
```

The exported source and the managed Forge project may evolve independently.

An export is not a magic round-trip branch.

---

# 75. Rejected alternative — symbol reuse after deletion

Rejected because it creates semantic ambiguity.

Example:

```text
old fld_A → Email
deleted
new fld_B → Email
```

would make historical and archived source visually indistinguishable despite referring to unrelated fields.

Symbols remain tombstoned instead.

---

# 76. Rejected alternative — label-driven source renaming

Rejected because cosmetic UI changes would become source ABI changes.

---

# 77. Rejected alternative — compile every candidate transition

Rejected because incomplete user code would freeze unrelated visual editing.

Compatibility validation is impact-aware.

---

# 78. Rejected alternative — skip compilation for all spec changes

Rejected because breaking ABI changes could silently invalidate user code.

Class C transitions require candidate compatibility proof.

---

# 79. Rejected alternative — expose GORM models to before-hooks

Rejected because it leaks persistence implementation into the public extension contract.

Controlled draft/change APIs are used instead.

---

# 80. Rejected alternative — preserve deleted extension code under `internal/`

Rejected because dangling imports may poison subsequent module builds.

Archived code moves outside the active build graph.

---

# 81. Rejected alternative — infer rename by similar names

Rejected.

Without stable identity continuity:

```text
email disappeared
contact_email appeared
```

is ambiguous.

Forge does not use heuristic rename guesses for safety-critical migration intent.

---

# 82. Rejected alternative — generic frontend extension parity in F0

Rejected because the frontend ABI remains separately unsolved.

Backend rigor must not be projected onto React/TypeScript without an actual contract.

---

# 83. Consequences

## Positive

* ordinary relabeling rarely breaks custom code;
* duplicate human labels do not create source collisions;
* source symbols are deterministic and lifetime-unique;
* user code can remain temporarily broken without freezing unrelated visual edits;
* before-hooks can mutate safely without exposing GORM internals;
* update hooks can preserve presence semantics;
* deleted custom code is retained without poisoning builds;
* identity-aware migration inference fails closed after suspicious Git/hand edits;
* generated internals remain evolvable;
* user behavior remains ordinary statically compiled Go;
* no source reconstruction is necessary.

---

## Negative

* source symbols may retain old creation-time terminology;
* tombstoned symbols permanently consume human-readable names;
* explicit source normalization can be a substantial refactor;
* compatibility classification becomes a compiler responsibility;
* mutable extension drafts add ABI complexity;
* candidate validation may require a managed toolchain;
* Forge must maintain extension ABI compatibility intentionally;
* archived extensions require lifecycle UX and metadata;
* Git hand-edits to stable identity may require manual repair.

These costs are accepted.

---

# 84. F0 mandatory proof: symbol allocation

F0 must prove:

```text
Create Email      → Email

Relabel Email
→ Primary contact → code remains Email

Create new Email  → Email2

Delete old Email  → Email remains reserved

Create another
Email             → Email3
```

The exact suffixing scheme may change before lock, but lifetime collision prevention may not.

---

# 85. F0 mandatory proof: reserved symbols

F0 must include a case where a user creates an entity whose natural source symbol conflicts with a generated/framework-reserved identifier.

The project must:

* reject it with actionable feedback; or
* deterministically disambiguate it before commit.

It must never defer discovery to an arbitrary Go compiler collision.

---

# 86. F0 mandatory proof: neutral edit with broken custom code

Given:

```go
internal/extensions/customer/hooks.go
```

contains an unrelated syntax/type error,

a visual change such as:

```text
navigation label:
Customers → Clients
```

must still be accepted if Forge proves the extension ABI fingerprint is unchanged.

Runtime Build remains unhealthy.

The editor does not deadlock.

---

# 87. F0 mandatory proof: rename preserves extension ABI

Given a hook using:

```go
customer.Email()
```

when:

```text
Label:
Email → Contact email

Storage:
email → contact_email
```

then:

* stable ID is unchanged;
* code symbol remains `Email`;
* ABI fingerprint remains unchanged;
* hook remains untouched;
* migration intent is rename;
* candidate may commit without requiring the existing hook implementation to build.

---

# 88. F0 mandatory proof: BeforeCreate mutation

A before-create hook must be able to:

```text
read field
normalize field
write field
reject invalid field
```

using only the supported extension API.

Example behavior:

```text
" USER@EXAMPLE.COM "
        ↓
"user@example.com"
```

before persistence.

---

# 89. F0 mandatory proof: BeforeUpdate presence

An update hook must distinguish:

```text
field absent
```

from:

```text
field present with empty/zero value
```

and must be able to replace the candidate changed value.

---

# 90. F0 mandatory proof: extension addition

Given a resource already containing persisted data,

enabling an extension must:

* add the generated contract;
* create user stub only once if requested;
* leave data untouched;
* never rewrite the stub on future regeneration.

---

# 91. F0 mandatory proof: dependent deletion

Deleting a resource that is referenced by:

```text
another relationship
+
active custom extension
```

must fail before the invalid state becomes current.

After dependencies are explicitly resolved and deletion proceeds, user code is archived outside the build path.

---

# 92. F0 mandatory proof: explicit source refactor

Normal relabel:

```text
Customer → Client
```

must preserve:

```go
CustomerView
```

An explicit code refactor:

```text
Customer → Client
```

must:

* alter the candidate ABI;
* be classified breaking;
* identify extension incompatibilities;
* remain uncommitted until resolved.

---

# 93. F0 mandatory proof: type change

An extension-visible field change:

```text
int → string
```

must be detected as source ABI-breaking even though stable identity remains unchanged.

---

# 94. F0 mandatory proof: identity discontinuity

Given a trusted prior spec:

```text
fld_A → email
```

and externally modified current spec:

```text
fld_B → contact_email
```

Forge must refuse to infer a rename automatically.

The safety model must fail closed.

---

# 95. F0 mandatory proof: user code preservation

Hash the user extension implementation before regeneration.

Run multiple compiler mutations.

Assert that Forge-owned generation never modifies the file contents.

---

# 96. F0 mandatory proof: archival outside build graph

Delete a resource with custom source.

Approve archival.

Then run:

```bash
go build ./...
```

The archived source must not poison the active module.

# 98. F0 exit gate

F0 is complete only when all of the following are true:

1. stable semantic IDs work;
2. symbols are deterministically minted;
3. source-symbol collisions are resolved before commit;
4. deleted symbols remain tombstoned;
5. reserved generated symbols cannot collide;
6. normal visual renames preserve extension ABI;
7. ABI-neutral edits remain possible while unrelated user code is broken;
8. BeforeCreate supports safe mutation and structured rejection;
9. BeforeUpdate preserves presence semantics;
10. regeneration never rewrites user extensions;
11. deleted-resource extension source is archived outside the active build graph;
12. dependency-breaking deletion fails before commit;
13. explicit source renames are recognized as breaking;
14. extension-visible type changes are recognized as breaking;
15. identity discontinuity disables automatic rename inference;
16. the generated application still builds and runs as an ordinary Gombit application;
17. the integration with Gombit uses the intended versioned machine boundary.

If these properties cannot be demonstrated without Forge mutating arbitrary user implementation code, this ADR has failed and must be revisited.

---

# 99. Architectural invariants

## Invariant A — Identity

Semantic identity is represented by stable IDs, not names.

## Invariant B — Lifetime symbol uniqueness

A frozen source symbol cannot silently acquire a second semantic meaning later in the project's life.

## Invariant C — Presentation independence

Changing human-facing wording does not silently become a source-code refactor.

## Invariant D — Ownership

Forge never destroys or silently rewrites user-owned business logic.

## Invariant E — Narrow ABI

Extensions depend only on explicitly supported generated contracts.

## Invariant F — Controlled mutation

Before-hooks may mutate candidate application values without receiving raw persistence internals.

## Invariant G — Impact-aware validation

Forge does not require irrelevant user code to compile for an ABI-neutral visual edit.

## Invariant H — Breaking changes are gated

A candidate source ABI break cannot silently enter the current revision.

## Invariant I — Active tree validity

Preserved obsolete custom code cannot remain in a location that intentionally poisons future application builds.

## Invariant J — Safety fails closed

When Forge cannot prove semantic identity continuity, it does not guess migration intent.

## Invariant K — No round-trip illusion

Exported provenance metadata does not imply arbitrary source-to-spec reconciliation.

---

# 100. Final decision

The core rule of Gombit Forge remains:

> **Forge owns application structure; developers own custom behavior behind explicit seams.**

ADR-001 v2 strengthens that rule with two additional requirements:

> **Every generated source symbol is minted once, collision-checked, and lifetime-reserved against a stable semantic identity.**

and:

> **Forge validates changes according to their actual ABI impact: harmless structural edits remain usable even during broken user work, while true contract changes are blocked until compatibility is proven.**

If F0 cannot satisfy those three statements simultaneously, the extension architecture is not viable and must be redesigned before the visual editor is built.
