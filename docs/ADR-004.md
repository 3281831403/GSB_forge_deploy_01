# ADR-004 — Generation Ownership: Framework Primitives vs Application Synthesis

**Status:** Accepted
**Product:** Gombit Forge
**Repository:** `gombit-forge`
**Decision scope:** Which system generates resource-specific application code, and on what terms
**Amends:** DESIGN.md P4 — the amended text is applied in DESIGN.md itself; §4 below records the change and its rationale
**Related:** DESIGN.md §9, §14, §32 (M0); ADR-001 §15–19, §68–69

---

# 1. Summary

The dividing line is:

> **Gombit owns framework primitives; Forge owns application synthesis.**

Forge generates resource-specific application code — models, handlers, routes,
admin declarations and Forge extension points — under
`internal/forge_generated/**`.

Gombit continues to own the CLI and bootstrap, migrations, ORM integration,
OpenAPI, the TypeScript client, auth and admin infrastructure, embedding, and
framework-level machinery generally.

The binding constraint on that grant:

> **Forge-generated output must consume Gombit's public/stable APIs rather
> than duplicating Gombit's infrastructure.**

---

# 2. Context

DESIGN.md P4 forbids Forge from independently implementing a list that
includes **resource scaffolding semantics**. Read literally, that forbids the
model/handler/route generator M0 requires, so the M0 gate could not be built
without resolving the conflict.

Three facts make this more than a wording problem.

## 2.1 ADR-001 mandates a layout Gombit cannot emit

ADR-001 §15 requires:

```text
internal/forge_generated/<resource>/
    model.go  contract.go  handlers.go  routes.go  extension_api.go
```

kept strictly disjoint from user-owned `internal/extensions/**` (D7), with
`extension_api.go` carrying the versioned extension ABI (D9) — immutable
views, create drafts, update change sets, structured field references.

Gombit's `resourcegen` writes `internal/<name>/{<name>,handler,routes}.go`
and has no concept of an extension ABI. The layouts are not reconcilable by
configuration.

## 2.2 The reuse path DESIGN.md §9 describes does not exist as an API

§9 says the compiler "may reuse Gombit's generator packages directly rather
than spawning CLI commands where practical." Verified against gombit v0.1.5,
the entire exported generation surface of `resourcegen` is:

```go
func Generate(ctx context.Context, opts Options) error
```

Every renderer (`renderModel`, `renderHandler`, `renderRoutes`, …) is
unexported. `Generate` additionally:

* requires a materialized app tree (`go.mod`, `cmd/server/main.go`,
  `internal/platform/database.go`) and reads `gombit.yaml` and the frontend
  from disk;
* operates on exactly one resource per call — the chatty protocol ADR-001 §69
  rejects;
* AST-mutates `cmd/server/main.go` and `internal/platform/database.go`;
* wires `AutoMigrate`, which DESIGN.md §14 forbids in deployed applications;
* writes to a fixed output directory.

There is no pure `render(spec) → files` seam to call. "Reuse the packages" is
not available without first re-architecting another repository's generator.

## 2.3 The model does not fit

`resourcegen` supports 6 scalar types (`string, text, int, int64, bool,
uint`) against Forge's 9 MVP field types, and refuses the `references=`
modifier, so it cannot express a relationship at all. `belongs_to` is the
backbone of the Forge domain graph.

# 3. Decision

## D1 — Forge owns application synthesis

Forge generates, under `internal/forge_generated/**`:

* GORM models
* Huma handlers and request/response contracts
* route registration
* admin declarations
* the extension API surface (views, drafts, change sets, field references,
  hook registration)
* the frontend's generated configuration and pages under
  `frontend/src/forge_generated/**`

This is derived from `ProjectSpec`, is wholly compiler-owned, and may be
deleted and recreated at will (ADR-001 §16).

## D2 — Gombit owns framework primitives

Forge must not reimplement, wrap-and-replace, or fork:

* the CLI and application bootstrap (`gombit new`)
* migration generation and execution (Atlas)
* ORM integration (GORM)
* OpenAPI document generation
* TypeScript client generation
* authentication and session/cookie infrastructure
* admin infrastructure (the admin runtime, data plane and SPA)
* embedded builds (`gombit build --embed`)
* routing, config, logging and the rest of the framework runtime

If Forge needs framework behavior that also belongs in ordinary Gombit
applications, the P4 preference stands unchanged: **add it to Gombit first.**

## D3 — Generated output consumes Gombit's public APIs

This is the constraint that keeps D1 from becoming a second framework.

Forge-generated code must be an ordinary consumer of Gombit's public, stable
packages — importing `framework`, `contract`, `auth`, `database`, `admin` and
registering through their documented entry points.

Explicitly forbidden in generated output:

* a Forge-specific router, middleware chain, or request lifecycle
* a Forge-specific ORM layer or query builder over GORM
* a Forge-specific auth, session, permission or admin implementation
* a Forge-specific response envelope that diverges from Gombit's D10 shape
* vendored, copied or forked Gombit internals
* imports of Gombit *internal* packages

If generated code cannot express something through a public Gombit API, that
is a signal to extend Gombit (D2), not to synthesize a private replacement.

## D4 — The Gombit boundary stays coarse

Forge invokes Gombit through project-level operations (ADR-001 §68–69):
scaffold the application, generate migrations, emit OpenAPI, generate the
TypeScript client, build. Never one invocation per resource, page or field.

`gombit make resource` is a developer convenience for hand-written
applications. Forge does not drive it.

## D5 — The pinned version is ≥ v0.1.12

The module path was renamed at v0.1.2 from
`github.com/LAA-Software-Engineering/gombit` to `github.com/gombit-dev/gombit`;
generated applications require the latter, which set the original ≥ v0.1.2
floor. The floor advanced to **v0.1.11**, which added the declared server-side
list filtering/sort/search (gombit #260) that generated list handlers consume,
then to **v0.1.12**, which added the declared server-side numeric aggregate
contract (gombit #273) that generated dashboard aggregate cards consume — an
older toolchain scaffolds a tree whose list pages cannot honor the spec's
search/filter/sort or reduce a numeric field server-side. ADR-001 §68 requires
the version to be pinned and recorded in export metadata; the floor lives in
`internal/gombit.MinimumVersion`.

## D6 — Generated applications keep no Forge dependency

Unchanged from DESIGN.md D2/P5 and restated because D1 makes it easier to
violate: generated output must not import Forge, call a Forge service, or
require Forge to run. A deployed application keeps working if Forge disappears.

# 4. Amendment to DESIGN.md P4

P4's forbidden list currently reads, in part:

```text
* resource scaffolding semantics
```

That bullet is amended to:

```text
* resource scaffolding semantics for hand-written Gombit applications
  (`gombit make resource`). Compiling a ProjectSpec into resource-specific
  application code under internal/forge_generated/** is Forge's own
  responsibility — see ADR-004 — and remains subject to ADR-004 D3:
  generated output consumes Gombit's public APIs and never duplicates
  Gombit infrastructure.
```

Every other P4 bullet is unchanged and remains binding, as does P4's closing
preference for adding capabilities to Gombit first.

# 5. Consequences

## Positive

* M0 is unblocked without pretending P4 says something it does not.
* The `internal/forge_generated/**` layout and the extension ABI in ADR-001
  become buildable.
* Determinism stays under Forge's control, which is a hard M0 acceptance
  criterion; it could not be guaranteed through another repo's CLI.
* Gombit is not forced to absorb Forge-shaped requirements into a
  general-purpose scaffolder.
* Ownership is legible: one sentence decides which side any future generator
  question falls on.

## Negative

* Two code generators exist in the ecosystem, and a Gombit change to model or
  handler conventions can leave Forge's output stylistically divergent.
* D3 is a standing review obligation rather than something a compiler checks;
  drift toward a private framework would be gradual and must be caught in
  review.
* Forge tracks Gombit's public API surface and absorbs its breaking changes.
* The field types Forge supports and `gombit make resource` supports may
  diverge, which is confusing for a user who has seen both.

# 6. Rejected alternatives

## 6.1 Extend `resourcegen` and call it as a library

Rejected for M0. It requires not only additive work (5 field types,
relationships) but re-architecting Gombit's generator: exporting a pure
render seam, decoupling it from filesystem access and `main.go` AST
mutation, and making the output directory configurable. Those are structural
changes that serve Forge rather than Gombit's own users, and they would block
the go/no-go gate on another repository's release cycle.

Adding the missing *field types* upstream remains worthwhile on its own
merits and is not foreclosed by this ADR.

## 6.2 Drive `gombit make resource` once per resource

Rejected. It is the chatty protocol ADR-001 §69 names, cannot express
relationships or 5 of 9 field types, writes the wrong ownership layout, and
wires AutoMigrate into deployed applications against DESIGN.md §14.

## 6.3 Fork or vendor `resourcegen`

Rejected. A fork inherits the layout and AutoMigrate problems while adding a
permanent merge burden, and D3 exists precisely to prevent copied Gombit
internals.

## 6.4 Leave P4 unamended and generate anyway

Rejected. It leaves the authoritative document contradicting the code, which
is the ambiguity this ADR exists to remove.
