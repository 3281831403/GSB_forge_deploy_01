# ADR-005 — Forge / Cloud Boundary: Authoring Loop vs Runtime Primitives

**Status:** Accepted — locked before PR #100 (#38 deploy models) merges and
before #101 (the initial control-plane Atlas migration) is authored. Execution
(the PR #100 disposition, the Cloud r1 sign-off for D5) is tracked separately.
**Product:** Gombit Forge
**Repository:** `gombit-forge`
**Decision scope:** Which product owns build execution, environments, managed
databases, secrets, deployment, routing, logs and health — and how Forge drives
them without becoming a private PaaS
**Supersedes (in part):** DESIGN.md §5 (control-plane box), §11–13, §15, §21,
§24–27, §25's AWS stack, and the M4–M6 milestone descriptions. Each superseded
span is enumerated in §4.
**Amends:** DESIGN.md D3/D4/D8/D9 — unchanged as decisions, but now *realized in
Gombit Cloud*, not in Forge (§4.3)
**Related:** `gombit-cloud` RFC v0.1 (the counterpart boundary from Cloud's
side); ADR-001 §1 ("local-first"), §68–69 (coarse Gombit boundary), and its
reserved ADR-002 (Managed Local Toolchain & Runtime Preview) and ADR-003
(Gombit Migration Intent & Safety Manifest); ADR-004 (generation ownership);
DESIGN.md §31 (MVP loop), §33 (locked decisions)

---

# 1. Summary

Forge's MVP design (DESIGN.md §5, §11–15, §24–27) has the Forge control plane
own builds, deployments, environments, managed PostgreSQL, secrets, routing,
TLS, logs, health and rollback — and names a full AWS stack (ECS/Fargate, ECR,
RDS, S3, Route 53, ACM, ALB, Secrets Manager, SQS) to implement them. That is a
managed deployment platform. `gombit-cloud` now exists and its RFC claims
exactly that surface.

The dividing line this ADR sets:

> **Forge owns the authoring loop; Gombit Cloud owns the runtime primitives.**

Forge edits `ProjectSpec`, compiles it to an ordinary Gombit application,
versions revisions, and drives the user-facing loop — preview, deploy, view
logs, export. It does **not** provision or operate infrastructure. Every
runtime primitive — build execution, artifact storage, environments (preview
and production), managed PostgreSQL, migration application, secrets, domains,
TLS, routing, runtime logs, health checks, rollback — is a Gombit Cloud
capability that Forge *invokes as a client*.

The seam between them is not a Forge↔Cloud private API. It is the **Gombit
application contract** (`gombit-cloud` RFC §9) plus the **migration safety
manifest** (ADR-003), both of which live upstream in MIT-licensed Gombit. Cloud
consumes that contract from *any* Gombit application, handwritten or
Forge-generated; Forge is one producer among others.

Forge must not implement a parallel runner. There is no "thin local PaaS" in
Forge for the MVP — the compiler's local toolchain (ADR-002) exists to
*generate and validate*, not to host deployed applications.

# 2. Context

## 2.1 The design welded two products together

DESIGN.md was written before `gombit-cloud` existed, so it folded the runtime
platform into Forge. The result, read against the current issue tracker, is that
Forge's M4–M6 are a from-scratch PaaS:

* **M4** (#58–#67): SQS build queue, disposable build workers, container build,
  push to ECR, artifact storage to S3, AWS IaC.
* **M5** (#68–#72): preview environment provisioning (container + ephemeral
  Postgres), ALB + Route 53 + ACM routing.
* **M6** (#73–#79): RDS provisioning, Secrets Manager injection, migration
  preflight/apply, container rollout, health checks, traffic routing, rollback.

The control plane's model set is mid-flight:

* **#37 (`internal/project`: `Project`, `Revision`) is merged to `main`.** This
  is authoring-loop state and stays in Forge (D1/D6).
* **#38 (`internal/deploy`: `Environment`, `Build`, `Deployment`, `Domain`) is
  open PR #100, not merged.** `platform.Models()` adds them *on that branch*
  only — the §11 `Build` state machine, the `Deployment → revision + build`
  reference, the `Domain` model. The secrets store (#41) is not started.

None of the #38 set is Forge-specific. It is generic Gombit-application
operations, and it is precisely what `gombit-cloud` RFC C1–C8 (§89–96) claims.
Merging PR #100 as written, then building M4–M6 as written, would create two
products that both own build, deployment, environment, database, secret,
domain, log, health and rollback.

## 2.1.1 The intervention point is PR #100, before #101

The welding is not shipped code to unwind — it is an **open pull request**.
That is the cheapest possible moment to act: revise or hold PR #100 so the
deploy models never merge, rather than merge and extract later.

Reinforcing that: **#101 (the initial control-plane Atlas migration — foreign
keys, ON DELETE rules, the Deployment↔Build composite key, the `Build` state
CHECK, immutability triggers) is an open issue, not built.** No committed schema
pins these tables yet. If PR #100 merges *and* #101 then commits its schema over
`Environment/Build/Deployment/Domain`, those tables become the control plane's
schema of record and pulling them back out becomes a real migration with
compatibility obligations.

So this ADR wants to land **before PR #100 merges**, and #101 must be authored
against the reduced model set — Project + Revision + Forge tenancy + audit + the
`cloud_project_id` linkage — not the #38 set.

## 2.2 Cloud already states the boundary from its side

The `gombit-cloud` RFC is unambiguous and stricter than a naive "Forge → Cloud"
split:

* **C0 (§7, LOCKED):** Cloud must deploy an ordinary *handwritten* Gombit app
  before any Forge integration exists. Forge metadata may never be *required*
  to deploy (Invariant B, L2, L3).
* **§9 application contract, §69 / L4:** the cross-product contracts — build
  interface, migration manifest, health convention — live upstream in Gombit,
  not privately in Cloud (and, by symmetry, not privately in Forge).
* **§74 (anti-goal):** Cloud must never become an execution engine for
  `ProjectSpec`. The required path is `ProjectSpec → Forge compiler → Gombit
  application → Cloud`.
* **§97 (C9):** Forge integration is the *last* milestone and consumes normal
  Gombit build artifacts. Forge stays optional.

So the un-welding already exists on Cloud's side. What remains is to reconcile
*Forge's* documents and milestones to it. This ADR is that reconciliation.

## 2.3 The seam is licensing-forced, not merely tidy

The three products carry three licenses: Gombit MIT, Forge AGPL-3.0-or-later,
Cloud proprietary (`gombit-cloud` RFC §70). A proprietary Cloud cannot take the
cross-product contract from AGPL Forge without AGPL reach. Putting the build
contract, migration manifest and health convention in **MIT Gombit** (ADR-003
for the manifest; a Gombit build/health contract for the rest) is what lets
proprietary Cloud consume them cleanly. The boundary is not a preference we can
later blur; the license split enforces it.

## 2.4 It is also latent in ADR-001

ADR-001 §1 already describes Forge as **"local-first,"** reserves **ADR-002
(Managed Local Toolchain and Runtime Preview)** for the local toolchain, and
reserves **ADR-003 (Gombit Migration Intent & Safety Manifest)** for exactly the
manifest Cloud RFC §29–31 verifies. ADR-001 §2010/§2655 already say migration
SQL/manifest enforcement "belongs primarily to ADR-003/Gombit." DESIGN.md's
cloud-heavy M4–M6 were the outlier, not this ADR.

# 3. Decision

## D1 — Forge owns the authoring loop

Forge owns, end to end:

* the visual editor and `ProjectSpec` (D1 spec-first)
* the compiler (`ProjectSpec → ordinary Gombit application`, ADR-004)
* project revisions and their lineage (DESIGN.md §8; ADR-001 §31)
* Forge tenancy — Organization / Member / Invitation and Forge roles
  (DESIGN.md §22; already built, #36)
* the control-plane audit log of *Forge* actions (DESIGN.md §23)
* source export (DESIGN.md §28; M7) — unchanged and still mandatory (D10)
* the **user-facing** loop: the Deploy tab, the "Preview" and "Deploy"
  actions, build-status surfacing, and the log viewer *as UI that reads Cloud's
  APIs*

The user loop is Forge's. The primitives it drives are not.

## D2 — Gombit Cloud owns the runtime primitives

Forge must not implement, provision, or operate:

* build execution, build workers, build queues, artifact storage, container
  images or a container registry
* environments — preview or production — or their lifecycle
* managed PostgreSQL (provisioning, credentials, backups, restore)
* migration *application* (verification and apply against a live database)
* the secrets store and runtime secret injection
* domains, TLS certificates, routing, load balancing
* runtime application logs, health checks, traffic promotion, rollback
* any AWS (or other provider) infrastructure for the above

Each of these is a Gombit Cloud responsibility (`gombit-cloud` RFC §3.3,
C1–C8). If Forge needs one, it calls Cloud.

## D3 — The seam is the Gombit application contract, not a Forge↔Cloud API

Forge deploys the way any producer does: it compiles `ProjectSpec` to an
ordinary Gombit application whose repository satisfies the Gombit application
contract (`gombit-cloud` RFC §9) and carries a migration set with its safety
manifest (ADR-003). Forge submits that **source revision** to Cloud; Cloud
builds it into an immutable artifact and operates it.

Consequences that are *not* negotiable:

* Forge sends Cloud a Gombit application, never a `ProjectSpec`. Cloud never
  interprets `ProjectSpec` (`gombit-cloud` RFC §74).
* The build of record is Cloud's immutable artifact (`gombit-cloud` RFC L5).
  Forge's local `gombit build` (ADR-002 toolchain) is for generation and
  validation only, never the deployed artifact.
* Anything Forge would want to add as "Cloud metadata" must be *enrichment* on
  top of the neutral contract, never a precondition for deploying — otherwise
  C0/L2 regress.

## D4 — Forge does not run a parallel runner

For the MVP there is no Forge-owned local or hosted runtime that serves deployed
applications. Preview and production both resolve to Cloud environments. The
"local-first" toolchain of ADR-001/ADR-002 covers compiling, generating
migrations, and validating a build — not hosting a running app for users.

Rationale: a parallel runner is the exact partial welding this ADR removes. Two
runtimes would double the operational surface, split the migration-safety story,
and reintroduce the coupling Cloud's C0 gate forbids.

## D5 — Preview is a Cloud primitive, pulled forward

Forge's MVP loop (DESIGN.md §31) requires `Preview → Deploy`. Cloud's RFC
originally deferred preview environments to C9 (§46–47) and production to C4
(§92). To let the Forge MVP land without Forge growing its own runtime:

* **Ephemeral preview environments move forward to Cloud C0/C1** as a
  first-class runtime primitive (isolated runtime + ephemeral data, `gombit-cloud`
  RFC §46, §85).
* **Production deployment stays at Cloud C4.**
* Forge *triggers* previews and *surfaces* their URL, state and logs through
  its Deploy tab; Cloud provisions and runs them.

This decision belongs to Cloud's roadmap and is recorded here only as the Forge
dependency it creates; the authoritative change is a `gombit-cloud` RFC revision
moving preview into C0/C1. Forge's M5 becomes "consume Cloud preview," not
"build preview infrastructure."

## D6 — Model ownership split

Forge's control plane keeps only what the authoring loop needs; Cloud owns the
runtime records.

| Model | Owner |
| --- | --- |
| `Organization`, `Member`, `Invitation` | Forge (tenancy of the builder) |
| `Project`, `ProjectRevision` | Forge |
| Forge `AuditEvent` (control-plane actions) | Forge |
| `Build`, `Deployment` | Cloud |
| `Environment` (preview / production) | Cloud |
| `Database` | Cloud |
| `Secret` | Cloud |
| `Domain` | Cloud |
| Runtime `AuditEvent` (deploy/migration approval/secret change) | Cloud |

Forge's `Project` carries a **linkage** to its Cloud counterpart (e.g.
`cloud_project_id`) and nothing more of Cloud's schema. A Forge deploy is
conceptually:

```text
revision  := forge.CurrentRevision(project)
source    := compiler.Compile(revision.Spec)     // ordinary Gombit app
build     := cloud.CreateBuild(cloud_project_id, source)
cloud.Deploy(environment = "production", build = build)
```

Forge never models an ECS task definition, an ALB target group, an ECR tag or a
deployment rollout. Cloud understands those.

## D7 — Contracts live upstream in Gombit

The build interface, health convention and migration safety manifest are Gombit
concerns (`gombit-cloud` RFC §69/L4; ADR-003). They are not authored in Forge
and not authored in Cloud. Where Forge needs one that does not yet exist, the
P4 rule stands: **add it to Gombit first** (ADR-004 D2).

# 4. Reconciliation with DESIGN.md

DESIGN.md remains authoritative for the authoring loop. The following spans are
superseded by this ADR and should be revised to defer to Gombit Cloud. Until
that doc surgery lands, this ADR governs on conflict.

## 4.1 Superseded — moves to Gombit Cloud

* **§5 architecture diagram** — the "Forge Control Plane" box lists Builds /
  Deployments / Environments, and the diagram continues into Build Worker and
  Runtime Platform. Trim the control-plane box to Projects / Specs / Users /
  Organizations / Revisions + a Cloud linkage; the Build Worker and Runtime
  Platform boxes become Gombit Cloud, drawn as a downstream product.
* **§11 Build system** → Cloud C1 (`gombit-cloud` RFC §11–16, §89).
* **§12 Deployment model** (isolated container per project) → Cloud C4 (RFC
  §21–23, §56, §92).
* **§13 Database model** (managed PostgreSQL) → Cloud C2 (RFC §25–28, §90).
* **§15 Deployment safety** (preflight, apply, health, route) → Cloud C3/C4
  (RFC §22, §29–33, §91–92).
* **§21 Secrets** (the managed store; "write-only after creation") → Cloud C5
  (RFC §38–39, §93). Forge's *spec* rule — secrets never live in `ProjectSpec`
  — stays in Forge.
* **§24 Observability** (runtime logs, health, histories) → Cloud C6 (RFC
  §40–42, §94). Forge keeps only the Deploy-tab *view* onto Cloud logs.
* **§25 Infrastructure** (the entire AWS stack) → Cloud §58 (PROVISIONAL). No
  provider names belong in Forge docs.
* **§26 Build execution** (SQS, build workers) → Cloud §14, §89.
* **§27 Security boundaries** (isolated, untrusted build) → Cloud §15, §76, L13.

## 4.2 Retained in Forge

§7 (`ProjectSpec`), §8 (revisions), §9 (compiler), §10 (generated ownership),
§16 (preview **UX** — the debounce/trigger behavior, not the environment),
§17–19 (editor / pages / branding), §22 (Forge tenancy), §28 (export),
§29 (Forge version metadata), §31 (MVP loop).

**§23 (Forge audit log) is retained, with its action list reduced** — a third
category between §4.1's superseded spans and the cleanly-retained ones above.
The section stays (Forge keeps an audit trail of its own actions), but the
runtime lifecycle events it listed (deployment started / succeeded / failed) and
`secret changed` are Gombit Cloud's audit trail (`gombit-cloud` RFC §62), not
Forge's. Forge records the *trigger* of a preview or deploy, never the runtime
lifecycle. DESIGN.md §23 carries the reduced list and a marker; the audit
vocabulary (`controlplane/internal/audit`) is the closed set enforced in code.

## 4.3 Locked decisions — realized in Cloud, not re-litigated

DESIGN.md §33 decisions survive; their *implementation site* moves:

* **D3 isolated per project** — implemented by Cloud runtime isolation
  (`gombit-cloud` RFC §56, Invariant F).
* **D4 PostgreSQL only (managed)** — Cloud's managed-DB scope (RFC L7, §25).
* **D8 builds are asynchronous** / **D9 build execution is isolated** — Cloud's
  build workers (RFC L13, §14–15). Forge no longer needs these as its own
  invariants because Forge no longer builds.

`D2` (compiler, not runtime), `D10` (export mandatory), `D11` (no round-trip),
`D12` (use Gombit's contracts) are untouched and this ADR strengthens them.

**Where an amended locked decision is marked (convention, precedent for future
ADRs).** An amended locked decision is annotated **at its canonical definition
first** — DESIGN.md §33 and AGENTS.md's "Locked decisions" list, the two places
an agent is told to treat as authoritative for the locked set — and *also* at the
sections that depend on it (§12/§13/§26/§27 here). §4.1's per-span markers set
the pattern for superseded *scope*; an amended *decision* gets the same
treatment, with the definition carrying the marker so the sentence most likely
to be quoted back carries the qualifier. Marking only the dependent sections
leaves the definition reading as an unchanged Forge obligation, which is the gap
this convention closes.

## 4.4 Milestone re-scope

M4–M6 change from "Forge builds a PaaS" to "Forge integrates Gombit Cloud":

* **M4 — Build integration.** Forge submits a compiled source revision to Cloud
  and tracks the resulting build (state, logs) through Cloud's API. Delete the
  SQS / worker / ECR / S3 / IaC scope from Forge (it is Cloud C1). Issues
  #59–#67 move to `gombit-cloud` or close as superseded; the Forge-side
  remainder is "call CreateBuild + surface build state/logs."
* **M5 — Preview integration.** Forge triggers a Cloud preview environment
  (D5) and surfaces its URL/state/logs. The provisioning/routing issues
  (#69–#70) move to Cloud; Forge keeps the trigger/debounce/replace UX (#71)
  and the log-viewer UI (#72).
* **M6 — Deploy integration.** Forge invokes Cloud production deploy and
  surfaces status, including the destructive-migration approval gate (Cloud
  L9/§32) rendered in Forge's UI. RDS / Secrets Manager / rollout / routing
  issues (#74–#79) move to Cloud C4; the Forge-side remainder is the deploy
  action, the approval UX, and status surfacing.
* **Control-plane models.** #37 (`internal/project`: `Project`, `Revision`),
  already merged, stays. **PR #100 (#38, `internal/deploy`) does not merge as
  written** — it is revised to drop `Environment/Build/Deployment/Domain` (they
  move to `gombit-cloud`) or closed and re-opened at reduced scope; either way
  `platform.Models()` never gains them on `main`. Forge's `Project` gains a
  `cloud_project_id` linkage instead. #41 (secrets store) is redirected to
  `gombit-cloud` (C5) before any code is written.
* **#101 (initial migration) is authored against the reduced model set** —
  Project, Revision, Organization/Member/Invitation, audit, and the
  `cloud_project_id` linkage — not `Environment/Build/Deployment/Domain`. #101
  is blocked on both this ADR and the PR #100 disposition.

The PR #100 disposition, the issue edits/moves, and the `cloud_project_id`
linkage change are a follow-up, gated on human approval; this ADR only fixes the
target shape. Note the ADR itself is authored on a docs branch behind `main`
(which already carries #37) — the reduced-model changes land against `main`.

# 5. Consequences

## Positive

* One sentence decides every future "does this go in Forge or Cloud?" question:
  authoring loop vs runtime primitive.
* Forge stops carrying a from-scratch PaaS it does not need and cannot
  differentiate on. Its scope shrinks to the genuinely unique part — the
  spec-to-Gombit compiler and the visual editor.
* Cloud gets a first serious client (Forge) that forces a complete vertical
  slice — build, migrate, provision, deploy, log, redeploy — without Forge
  privileges leaking into Cloud's contract.
* The license split (MIT / AGPL / proprietary) stays clean because the seam is
  the MIT Gombit contract, not an AGPL Forge API.
* Handwritten Gombit apps and Forge apps deploy through the same Cloud path
  (`gombit-cloud` RFC Invariant B), which is a stronger product story than
  "Forge has a private PaaS."

## Negative

* Forge's MVP loop (§31) now depends on Cloud reaching preview (C0/C1) and
  production deploy (C4). Forge cannot ship its end-to-end loop before Cloud
  does. D5 mitigates this by pulling preview forward, but the coupling of
  *timelines* is real and must be planned across both repos.
* Some cross-product contract work (build interface, health convention) does
  not exist in Gombit yet and becomes a prerequisite, per D7. That is upstream
  work neither repo has scheduled.
* Two repos and one upstream must stay coordinated on the contract version
  (`gombit-cloud` RFC §53–55). A contract bump is now a three-repo event.
* Re-scoping M4–M6 and moving issues #41/#59–#79 is churn on an already planned
  milestone set, and it lands on an in-review PR: #38 (PR #100) must be revised
  or closed rather than merged, which is rework on code already through review.
  The cost is bounded only because #100 has not merged and #101 has not
  committed its schema yet — the window is open now and closes at those two
  events.

# 6. Rejected alternatives

## 6.1 Forge keeps its own PaaS (status quo of DESIGN.md)

Rejected. It duplicates all of `gombit-cloud` C1–C8, splits the migration-safety
story across two implementations, and violates the license seam by building the
runtime inside AGPL Forge. It also contradicts ADR-001's "local-first" framing
and its reserved ADR-002/ADR-003.

## 6.2 Forge keeps a "thin local runner" for its MVP

Rejected, and rejected explicitly by the roadmap decision behind this ADR. A
thin runner is partial welding: it reintroduces a second runtime, a second
migration-apply path, and a second isolation model, and it competes with the
Cloud path it is supposed to defer to. D4 forbids it.

## 6.3 Cloud consumes `ProjectSpec` directly

Rejected — it is Cloud's own anti-goal (`gombit-cloud` RFC §74). Cloud would
become a proprietary `ProjectSpec` interpreter, destroying export portability
(D11/H) and welding Cloud to Forge in the opposite direction.

## 6.4 Put the cross-product contract in Forge or in Cloud

Rejected. In Forge it is AGPL and Cloud cannot consume it cleanly; in Cloud it
is proprietary and handwritten Gombit apps cannot rely on it. It belongs in MIT
Gombit (`gombit-cloud` RFC L4/§69; ADR-003), which is the only placement that
serves both producers and the open ecosystem.
